## 1. `write_score_cache` 唯一约束崩溃（已修，请复核）

**位置**：`app/scoring/usecases.py:339` `write_score_cache()`

**根因链**：
1. 访客提交录音 → 管线把评分缓存写进 `score_cache`，键为
   `(owner_type, owner_id, pcm_sha256, level_id, content_version, rule_version, provider_version)`；
2. 注册并登录 → `bind_sid_to_user`（`app/identity/usecases.py:119`）调
   `migrate_score_cache_owner` 把该行**改键迁移到用户名下**；
3. 用户再提交一段**内容相同**的音频（pcm_sha256 一致）→ 管线内 `read_score_cache`
   未命中（迁移可见性与管线读存在竞态窗口），走 Provider 评分；
4. 收尾 `_finalize_completed` → `write_score_cache` **裸 INSERT** → 撞 UNIQUE 约束；
5. 异常被吞进执行器 future，录音永远停在 `processing / stage=queued`，
   30 秒后被调度器标 `TIMEOUT` 失败。用户视角：这次录音永远查不到结果。

**证据**（2026-10-15 复现）：
```
sqlalchemy.exc.IntegrityError: UNIQUE constraint failed:
score_cache.owner_type, score_cache.owner_id, score_cache.pcm_sha256, ...
[parameters: ('user', 'u_a7bdf...', ..., 'L30', 3, 'rules-1.0.0', 'mock-1.0.0', ...)]
```
DB 中该录音 `status='failed', stage='queued'`；服务日志
`WARNING svs.scheduler marked 1 recording(s) as TIMEOUT`。

**为什么 e2e 一直没抓到**：`e2e_test.py` 授权后的第二次提交用的是**女声**合成音频
（内容与首次男声不同、pcm_sha256 不同），不会撞键。`test_openapi_shapes.py`
两次都用同一份男声音频，稳定复现了此 bug。

**已做的修复**（前端会话，请后端复核思路与边界）：按 `migrate_score_cache_owner`
已有的查重模式改为**幂等更新**——同键则更新 `audio_id/payload/created_at`，无则插入。
修复后 `e2e_test.py` 77/77、`test_openapi_shapes.py` 58/58。

**建议后端顺带确认**：
- `run_pipeline` 对未预期异常的兜底：目前异常只进 future（异步路径无人 await），
  录音只能靠调度器 TIMEOUT 兜底。可考虑在 `run_pipeline` 外层 catch-all 落
  `failed(retryable=true)`，避免任何未来异常造成同样的滞留；
- 步骤 3 的读未命中原因（迁移 commit 与管线读的可见性竞态）未深挖，幂等写入已足够
  防崩，但若能解释清楚可在注释里补一句。

## 2. `wait_sync_window` 小同步窗口竞态（待修）

**位置**：`app/detection/usecases.py:170` `wait_sync_window()`

```python
try:
    await asyncio.wait_for(asyncio.wrap_future(future), timeout=config.SYNC_WINDOW_SECONDS)
except asyncio.TimeoutError:
    return outcome
```

**问题**：`asyncio.wait_for` 超时会**取消**被包装的 future。`concurrent.futures.Future.cancel()`
只在执行器线程**尚未开始**该任务时才会成功——于是：

- `SVS_SYNC_WINDOW=0`（或极小值）时，若线程池还没拾起任务，future 直接被取消，
  `run_pipeline` 永不执行，录音滞留 `processing`，直到调度器按 HARD_DEADLINE 标
  TIMEOUT。**已实测复现**：窗口 0 时提交返回 202，20 秒轮询全 202，
  DB 中 `stage='queued'`，33 秒后 `marked as TIMEOUT`；
- 窗口大（默认 8s）时线程早已启动、cancel 失败，所以线上默认配置不受影响。
  但该竞态在语义上是错的：同步窗口只是「等多久再回落 202」，不应有取消副作用。

**修复方向**（供参考）：不要把执行器 future 直接交给 `wait_for`，例如先
`asyncio.shield()`，或改成 `await asyncio.wait({task}, timeout=...)` 判定超时后不取消
任务本身；或给 wrap 加一层不可取消的桥接。修完后 `SVS_SYNC_WINDOW=0` 下
提交应收 202 且轮询最终 200。

**验证方式**：
```
# 清缓存避免 mock 评分缓存命中导致管线 <0.1s 完成直接返回 200
py -3.13 -c "import sqlite3; c=sqlite3.connect('data/app.db'); c.execute('delete from score_cache'); c.commit()"
SVS_SYNC_WINDOW=0 py -3.13 main.py        # 另一个终端
py -3.13 e2e_async_test.py                # 期望 3/3 PASS
```
（当前该测试在 `SVS_SYNC_WINDOW=0.05` + 冷缓存下可 3/3 通过，见 §5。）
